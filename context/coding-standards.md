# Kasheif — Coding Standards

Conventions observed in the existing codebase (`HalalStocks`, ASP.NET Core 8 MVC). Follow these for new work unless a file you're editing clearly does otherwise — in that case, match the surrounding file rather than "fixing" it as a drive-by.

## Naming Conventions
- Standard C#: PascalCase for classes/methods/properties, camelCase for locals/parameters.
- Interfaces prefixed `I` (`IRecommendationService`); implementation is the same name minus the `I` (`RecommendationService`).
- Controllers suffixed `Controller`; services suffixed `Service`. ViewModels are suffixed by role, not just "ViewModel": `*FormViewModel` (create/edit forms), `*IndexViewModel` (page-level list state), `*TableViewModel` (a reusable list partial's model).
- Boolean properties/fields read as a predicate: `IsHidden`, `IsExpiredMarker`, `IsAdmin`, `CanManage` — never `Hidden`, `Expired`, `Admin`.
- Migration names are descriptive PascalCase phrases of what changed (`AddIsHiddenToStockRecommendations`, `AddUserRecommendationsAndWalletExtras`), not generic (`Update1`).
- Arabic UI copy lives in `.cshtml` markup and in `[Display(Name = "...")]` on ViewModels — never hardcoded in `Models/`.

## File / Folder Structure
- `Controllers/` = public-facing; `Controllers/Admin/*` = admin-only, role-gated — this split mirrors the routing split (see below), keep new admin functionality there rather than branching inside a public controller.
- `Models/` = EF entities only. No validation attributes, no view/formatting logic.
- `ViewModels/` (public) vs `ViewModels/Admin/` — one file per view model.
- `Services/Interfaces/` + `Services/Implementations/` — always an interface + implementation pair, registered scoped in `Program.cs`, even for simple CRUD. New features should follow this rather than a controller calling `AppDbContext` directly (the one existing exception, `PortfolioRequestController`, is documented tech debt, not a pattern to repeat).
- `Views/{Controller}/` holds that controller's views. Partials shared within one feature are prefixed `_` and live alongside the feature's views (e.g. `Views/Recommendations/_RecommendationTable.cshtml`); partials shared more broadly go in `Views/Shared/`.
- `Migrations/` — one migration per schema change, generated via `dotnet ef migrations add`, never hand-edited afterward. Before considering a schema change done, confirm the migration `.cs` file, `AppDbContextModelSnapshot.cs`, the `__EFMigrationsHistory` table, and the live database all agree.

## Code Style
- Nullable reference types + implicit usings are on project-wide — respect `?`/nullability, don't silence with `!` unless genuinely guaranteed non-null by the surrounding logic.
- Attribute routing only (`[Route]`, `[HttpGet]`/`[HttpPost]`) — no conventional `{controller}/{action}` routing, no MVC Areas.
- All `DataAnnotations` validation belongs on ViewModels, not domain models — this is the single most consistently enforced rule in the codebase. Don't add `[Required]` etc. to a `Models/` class even for a "quick" fix.
- Decimal DB columns need explicit `HasPrecision(...)` configured in `AppDbContext.OnModelCreating` — EF does not infer precision by convention; a new decimal property without it is a bug, not a style nit.
- Uniqueness constraints are always explicit `HasIndex(...).IsUnique()` calls in `OnModelCreating` — never assumed from naming or FK shape alone.
- A shared list/table partial takes one parameterized ViewModel carrying the data, a permission flag (e.g. `CanManage`), URL prefixes, and a section key for multi-instance pages — follow the `RecommendationTableViewModel` / `_RecommendationTable.cshtml` pattern rather than forking the partial per role/audience.
- Every state-changing POST action pairs `[ValidateAntiForgeryToken]` with `@Html.AntiForgeryToken()` in the form. For `fetch`-based mutations, send the token in the `RequestVerificationToken` header (the name is set globally in `Program.cs`) — get it into JS via `@inject Microsoft.AspNetCore.Antiforgery.IAntiforgery` and `GetAndStoreTokens(Context).RequestToken`, as `Views/Calculator/Index.cshtml` and `CapitalPurification.cshtml` do. Don't copy the Zakat AJAX-delete, which skips CSRF entirely.

## Arabic Validation Messages

The site is Arabic-only, and English validation text used to leak through in three separate ways. All three are now handled globally — **do not hand-write Arabic strings for standard rules**, and don't re-introduce per-field workarounds:

1. **jQuery Validate built-ins** (`required`, `min`, `max`, `step`, `number`, `email`, …) — overridden in `wwwroot/js/validation-messages-ar.js`, loaded by `Views/Shared/_ValidationScriptsPartial.cshtml` **and** `Views/Recommendations/_FormScripts.cshtml`. Those are the only two places that pull in the validation plugins; a fix applied to just one misses four recommendation views. Note these rules fire off raw HTML5 `min`/`max`/`step` attributes, which jQuery Validate auto-detects — so an input with `min="0"` shows the *generic* message even when the ViewModel has a field-specific `[Range]`, because attribute-derived rules are checked first.
2. **Server-emitted model-binding messages** (`data-val-number`, "The value 'x' is not valid…") — Arabic accessors set on `options.ModelBindingMessageProvider` in `Program.cs`.
3. **Implicit `[Required]` on non-nullable value types** (`int CategoryId`, `decimal InvestmentCapital`, …) — MVC synthesizes a `RequiredAttribute` with no source attribute to annotate. `Helpers/ArabicValidationMessagesProvider.cs` (an `IValidationMetadataProvider`) fills in Arabic for any attribute left without an `ErrorMessage`, and pre-empts the value-type case by declaring its own `RequiredAttribute`. Note the framework builds the *client* adapter for non-nullable value types at client-validator time, bypassing an `IValidationAttributeAdapterProvider` — the metadata provider is the hook that actually works for both server and client.

Messages deliberately omit the field name: the ViewModels carry no `[Display]` names, so `{0}` would render an English property name inside an otherwise Arabic sentence.

`_ValidationScriptsPartial` also self-loads jQuery via the standard `window.jQuery || document.write(...)` fallback, so a view that forgets to include jQuery no longer silently breaks client validation (two wallet views were doing exactly that).

## Error Handling Approach
- Unhandled/unexpected errors are centralized: `app.UseExceptionHandler("/error/500")` + `app.UseStatusCodePagesWithReExecute("/error/{0}")`, handled by one `[Route("error/{code:int}")]` action in `HomeController`. Don't wrap controller actions in generic try/catch for this — it's already handled upstream.
- Expected validation failures use `ModelState.AddModelError(...)` and re-render the form view (see any `Create`/`Edit` POST action for the pattern) rather than throwing.
- Business-rule conflicts (duplicate recommendation for a stock, wallet purchase exceeding available cash, etc.) are checked explicitly in the controller *before* calling the service, surfaced as a friendly `ModelState` error — not left to bubble up as a raw DB constraint violation.
- No logging/telemetry framework beyond ASP.NET Core defaults was found — check `Program.cs` before assuming Serilog, Application Insights, or similar are wired up.

## Other Observable Conventions
- New features tend to reuse an existing pattern rather than introduce a new library or approach — e.g. the recommendations request/approval flow reused the `PortfolioRequest` pipeline shape, and its searchable stock dropdowns reused the existing Select2 setup instead of adding a new component. Check for a sibling feature solving the same shape of problem before building something new.
- Razor partial-view resolution is relative to the *rendering controller's* view folder, not the `.cshtml` file's own physical folder. A partial shared across controllers (e.g. between `RecommendationsController` and `InvestmentWalletController`) must be referenced by full path (`~/Views/Recommendations/_NavTabs.cshtml`), or it will throw `InvalidOperationException` when rendered from the "wrong" controller.
- No automated tests exist yet. Until a test project is added, a clean `dotnet build` plus manual verification of the actual flow you changed is the standard (and only) way to confirm correctness — don't treat a successful build alone as proof a feature works.
- **Conditionally-required fields on a shared form** (e.g. `GeneralTrend` is required on the admin recommendation form but optional on the private one, both sharing `StockRecommendationFormViewModel`) can't be expressed with a single DataAnnotation. The working pattern: (1) make the property nullable (`string?`) — ASP.NET Core implicitly treats non-nullable reference-type ViewModel properties as required (nullable reference types + default MVC validation), so a non-nullable `string` stays "required" even after removing `[Required]`; (2) gate the native HTML5 `required` attribute behind a context flag on the ViewModel (see `IsPrivate` on `StockRecommendationFormViewModel`) in the Razor partial; (3) enforce the actual rule server-side with an explicit `ModelState.AddModelError(...)` check in only the controller action(s) where it applies. See `Views/Recommendations/_FormFields.cshtml` + `RecommendationsController.Create`/`Edit` for the full pattern. *(This step list previously included hand-adding `data-val-required="<Arabic message>"` to beat jQuery Validate's English default — no longer needed, see **Arabic Validation Messages** above.)*
- **Bootstrap validation styling is hand-driven, not `was-validated`.** Nothing in the codebase uses `needs-validation`/`was-validated`. The idiom is a `data-field="PropertyName"` wrapper containing the control and an empty `<div class="invalid-feedback">`, plus a `setFieldState(field, message)` helper that toggles `.is-invalid` and writes the message, and a `validateForm()` returning a bool that gates submit. Forms using it carry `novalidate` to suppress the browser's own bubbles. See `Views/RealPortfolio/Index.cshtml` and `Views/Calculator/CapitalPurification.cshtml`. It needs three CSS rules (forcing `.invalid-feedback` to `display:block`) copied alongside it.
- **Select2 is the default searchable-dropdown, but not mandatory.** Two gotchas cost real time: the theme CSS path is `select2-bootstrap-5-theme@1.3.0/dist/select2-bootstrap-5-theme.rtl.min.css` — the `dist/css/...` variant **404s**, and Select2 then renders unstyled and borderless with no error. And a single-select always puts its search box *inside* the dropdown, which reads as a confusing "second field". Where a plain typed-in field is wanted instead, `Views/Calculator/CapitalPurification.cshtml` has a dependency-free autocomplete (debounced fetch → `.list-group` panel, arrow/Enter/Escape keys, outside-click close, and clearing the selection when the text is edited so a stale pick can't be saved).
- **Number formatting is per-page, and the locale choice is deliberate.** Most calculators format with `toLocaleString('ar-EG', …)`, which renders **Arabic-Indic** digits (`٤٠٬٠٠٠`). `Views/Calculator/CapitalPurification.cshtml` deliberately uses `'en-US'` (and `'en-GB'` for dates) for Western digits at the client's request. Don't "unify" one to the other without asking.
