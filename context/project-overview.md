# Kasheif — Project Overview

## Purpose
Kasheif ("كاشف" — revealer/discoverer) is an Arabic-language, Shariah-compliance screening platform for stocks on the Egyptian Exchange (EGX). Tagline: **"نقاء محفظتك، يبدأ من هنا"** ("Your portfolio's purity starts here"). It lets Egyptian investors check whether a stock is permissible to hold under Islamic finance principles, and if not fully, how much income must be purified (donated away). Content is explicitly informational, not financial advice.

- Live product name: **Kasheif**. Internal codebase/namespace: **HalalStocks** (solution `Kasheif`).
- Target audience: retail EGX investors, ranging from casual compliance-checkers to users who run their own purification/zakat calculations to a smaller segment wanting managed portfolios or curated recommendations.

## Core Features
Roughly free → gated, in order of engagement depth:

1. **Stock screening** (public, flagship) — filter EGX stocks by `ShariahStatus` (Halal / MustPurify / Prohibited / NotReviewed / AwaitingFinancialStatements / StatusBlocked), sector, and index. A finer-grained `PurityGrade` flags-enum captures nuance beyond a flat compliant/non-compliant call.
2. **Income purification calculator** (`/calculator`, titled حاسبة تطهير الدخل المحظور) — stateless: math runs client-side in JS, the server only renders a branded Arabic PDF (iText7) of the result; nothing is persisted. A separate, persisted **Calculations** feature (`/calculations`) lets logged-in users save/revisit sessions — same subject matter, different (service-backed, full-CRUD) architecture. Don't conflate the two.
3. **Zakat calculator** (`/zakat`) — zakat owed on a portfolio, referenced against a cached gold price (`GoldPriceSnapshot`) for the nisab threshold (in-memory cache → latest DB row → external GoldAPI call, in that fallback order).
4. **Capital purification calculator** (`/capital-purification`) — how much of the user's *capital* (not income) is exposed to riba, given the shares they own: `ownership% = owned ÷ Stock.TotalCompanyShares`, `capital share = Stock.TotalCompanyAssets × ownership%`, `purification = capital share × Stock.NonShariahInvestmentRatio`. Persisted per user as `CapitalPurificationRecord`, presented as two tables (لم يتم سدادها / تم سدادها) with an `IsPaid` toggle moving a row between them — the same paid/unpaid primitive `CalculationSession.IsPaid` already uses. **The server owns the arithmetic**: the client posts only `{ stockId, ownedShares }` and the controller recomputes everything from the stock's current data, so client-sent totals are never trusted. Every stock figure used is snapshotted onto the record, and `StockId` is nullable with `DeleteBehavior.SetNull`, so deleting a stock can never destroy or silently rewrite a user's saved history.
   - **Dividend purification calculator** (`/dividend-purification`, حاسبة تطهير توزيعات الأرباح) — guest-gated (`Views/DividendPurification/GuestGate.cshtml`), persisted per user as `DividendPurificationRecord` in the same unpaid/paid two-table shape as `/capital-purification` (`IsPaid` toggle, delete via Bootstrap modal). Layered like capital: `DividendPurificationController` → `IDividendPurificationService` → `AppDbContext`. **The server owns the arithmetic**: the client posts only `{ stockId, type: "cash"|"stock", cashAmount | shares + sharePrice }`; the controller recomputes `total` (cash amount, or shares × price) and `purification = total × Stock.PurificationRatio ÷ 100` from the stock's current data, so client totals/ratios are never trusted (the page's own math is just a live preview). (1) بيانات السهم — typeahead over `GET /api/stocks/dividend-search` returning the stock's `PurificationRatio` and its latest `StockFinancialReview.ReviewDate` (`IStockService.GetLatestReviewDatesAsync`); the user never types either. A stock with a NULL `PurificationRatio` (129/225 active stocks — mostly the non-compliant ones) is selectable but shows a message immediately and cannot be saved (also re-checked server-side). A ratio of 0 is valid and yields 0. (2) cash amount, or stock dividend as shares × price; (3) the read-only "نسبة الدخل المحظور" box just mirrors the ratio from (1). Every figure (ticker, name, ratio, statements date, inputs, totals) is snapshotted on the record, and `StockId` is nullable with `DeleteBehavior.SetNull`, so deleting a stock never rewrites history. Routes: `GET records`, `POST save`, `POST {id}/toggle-paid`, `POST {id}/delete` (CSRF header on all; ownership-checked by `UserId`). **The ratio source is `PurificationRatio`, by the client's direction** — admin-typed on the stock form only, never derived from reviews; `ProhibitedIncomeRatio` (172/226) is a separate field and differs from it on 4 stocks (ORWE, SPMD, ISMA, ADRI).
   - **Calculator instructions** (`/admin/instructions`, الإرشادات; `SuperAdmin,Admin` only) — the intro block at the top of the capital and dividend calculator pages is admin-editable, not hardcoded. A `CalculatorType` enum (`CapitalPurification = 1`, `DividendPurification = 2`, stored as int — never renumber) picks the calculator; a Quill editor holds that calculator's HTML. Storage is a two-column table `CalculatorInstructions` (`Type` = the enum, is the primary key; `ContentHtml`), seeded by the migration with the two original paragraphs (`Data/CalculatorInstructionDefaults.cs`). `ICalculatorInstructionService.GetContentAsync`: no row → built-in default; a saved-but-blank row (empty Quill `<p><br></p>` is normalized to null) → `null`, so the page shows **no** intro block; the public controllers put it in `ViewBag.Instructions` and the views `Html.Raw` it (same admin-trust model as article content, hence Editors are excluded). The guest-gate teaser pages keep their own fixed text (they exist for SEO) and are **not** driven by this. Switching the dropdown reloads `/admin/instructions?type=` so the editor opens with that calculator's saved text. **Images**: the editor's image button is overridden to upload via `POST /admin/instructions/upload-image` (same `IStorageService` as article images — R2 or local `wwwroot/uploads/instructions`; jpg/jpeg/png/webp only, no SVG, 5 MB cap) and insert the returned URL. Quill's default would embed base64, which blows the 20,000-char content limit, so pasted/dropped base64 images are deliberately dropped with a warning — don't remove that matcher.
   - The calculators above are grouped in the header under one **أدوات التطهير** dropdown (hover on desktop, tap on mobile), and all six user tools are surfaced as a card grid (**أدوات كاشف**) on the home page beneath the search results.
5. **Managed portfolio request** (lead-gen) — a form (capital, horizon, purity preference, contact method) feeding an admin pipeline: `New → UnderReview → Contacted → ActiveClient/Rejected`.
6. **Stock recommendations** (`/recommendations`, approval-gated) — admin-curated trade calls (trend, support/resistance, stop-loss, notes) per stock, plus each approved user's own private recommendation list. Requires an explicit request + admin-approval step (same gating shape as portfolio requests). The **page itself is publicly reachable**: a logged-out visitor gets a guest gate (see **Guest gates** below), a logged-in-but-unapproved user gets the existing `_AccessGate` partial. See **Recommendation visibility & validity** below for the current field-level behavior.
7. **Investment wallet** (`/recommendations/wallet`) — per-user paper-portfolio: a cash balance plus wallet items (stock, quantity, purchase/target/stop-loss prices), where each price can be sourced from a recommendation's levels or entered as a custom value. The stock picker pulls from both general and the user's own private recommendations. The wallet items table also shows each holding's stock sector (`StockCategories.NameAr`) beside the stock name. A per-wallet **max risk %** (`InvestmentWallet.MaxRiskPercent`, nullable) caps how much of the cash balance the wallet's total expected loss may represent; adding/editing an item, lowering the risk %, or reducing cash are all blocked (Bootstrap modal) if the action would push the wallet's actual expected-risk % (`ΣExpectedLoss / CashBalance × 100`) above that cap, and adding/editing items is blocked entirely until a risk % is set at all.
8. **Real portfolio** (`/recommendations/portfolio`, approval-gated — third tab beside التوصيات and المستشار الآلي) — per-user **real-money** tracking, deliberately independent of the wallet above: its own `RealPortfolio` (a `Capital` value) and `RealPortfolioItem` rows, so a paper trade in the wallet can never affect it. Each row is one **purchase lot** (`PurchaseDate`, stock, quantity, price) — the same stock may legitimately appear on several rows, so there is *no* unique `(PortfolioId, StockId)` index, unlike `WalletItem`. Four summary cards (رأس المال / رأس المال المستثمر / السيولة / صافي الربح-الخسارة, the last as value **and** a % of the amount *invested*, green/red). Only the purchase side is persisted (`TotalPurchase`, `PurchaseWeightPercent`); every market-derived figure (القيمة السوقية, ربح/خسارة, ربح/خسارة للسهم, نسبة الربح/الخسارة) is recomputed per request so it can't go stale in the DB. Guard rails mirror the wallet: a lot may not exceed available cash (`Capital − Σ TotalPurchase`, excluding the row being edited), and capital may not drop below the amount invested; lowering/raising capital recomputes every row's weight. The stock picker is a Select2-over-AJAX search across **all active stocks** (`/api/stocks/search`, matches ticker or Arabic/English name); picking one calls `/api/stocks/{id}/quote`, which returns sector, الحكم الشرعي and the live market price in one round trip. Both API routes return an explicit `403` rather than `Forbid()` — cookie auth would otherwise 302 them to the access-denied page, which `fetch` would try to parse as JSON.
   - **Market prices** come from `ITradingViewPriceService`, which POSTs to TradingView's keyless **scanner** endpoint (`TradingView:ScannerUrl`, default `https://scanner.tradingview.com/egypt/scan`, `ExchangePrefix` `EGX`) — batched into one request per page, cached per ticker in `IMemoryCache` (`CacheMinutes`, default 15). The endpoint is **unofficial and can break without notice**, so every failure is logged and swallowed, never thrown, and the last good price is persisted per row (`LastMarketPrice`/`LastMarketPriceAt`) as a fallback — the table then renders those values flagged stale, with a warning banner. A ticker TradingView doesn't cover (e.g. `AIHC`) simply shows "—" in the market columns and contributes 0 to the P&L totals. Note this means an unpriced holding still counts toward the invested denominator of صافي الربح/الخسارة %.
   - Admin-side management of this portfolio is **not** wired up — `/admin/wallet-management/{userId}` still exposes only its two original tabs.
9. **Articles** — admin-published content for SEO/education. Each article carries a required `ArticleCategoryId` FK to an `ArticleCategory` lookup table (managed on an admin "Manage Categories" page, with an inline "+ add category" affordance right on the article form so the admin doesn't have to leave it). A seeded fallback category ("عام", fixed `Id = 1`, exposed via `IArticleService.DefaultCategoryId`) backfills every article that existed before categories were introduced; it — and any category currently referencing articles — cannot be deleted (blocked via a Bootstrap modal, matching the `VideoCategory` pattern below). The public `/articles` listing adds title/content search plus a category filter, both composing correctly with the existing pagination and the `IsPublished`-only, newest-first ordering.
   - **Article kind** is an `Article.Type` enum (`Standard`/`ShariahStandard`/`Analytical`) — replaced an earlier `IsShariahStandard` bool once a third kind was planned, since one discriminator scales to future kinds without every query re-learning a new flag. `ShariahStandard` (admin toggle, independent of `IsPublished`) routes a published article into its own homepage section ("المعايير والضوابط وفقا للشريعة الإسلامية", capped at the latest 20 — an assumed limit pending client confirmation since there's no listing page for it yet); this exclusion is **homepage-only** — `/articles` (including its search/category filter) treats it as an ordinary published article. `Analytical` is excluded from both `/articles` and the homepage latest strip (see below). The admin list (`/admin/articles`) and detail-by-id lookup are unaffected by `Type` — both surface every article regardless of kind.
   - A category can be **auto-assigned** to a `Type` via `ArticleCategory.AutoAssignedForType` (nullable, resolved at runtime by `IArticleService.GetCategoryForTypeAsync` — never by name or a fixed Id) rather than picked manually; such a category is undeletable, same protection as "عام". Seeded example: "تحليلات وآراء" for `Analytical`.
   - **Opinions & Analysis (تحليلات وآراء) — complete.** Designated analysts (`AppUser.IsAnalyst`, toggled admin-side on `/admin/users/edit/{id}`, orthogonal to `UserRole` so an Admin can also be an analyst) get a public `AnalystProfile` (bio + photo) and author their own `Analytical` articles, which require admin approval (`Article.ApprovalStatus`: `NotRequired` for admin-authored content / `Pending` / `Approved` / `Hidden`) before `IsPublished` may be true — enforced as an invariant (`IsPublished ⟹ ApprovalStatus ∈ {NotRequired, Approved}`), never set directly by a controller. `IsAnalyst` is also mirrored into the auth claims (`AppUserClaimsPrincipalFactory`) as a second, independent `"Analyst"` role claim — note this only takes effect on the user's *next* sign-in, so any analyst-only action must re-check the DB flag, not just the claim (see `AnalystController.GetCurrentAnalystAsync`).
     - **Ownership of the state machine is split deliberately**: analyst-side self-service transitions (create → `Pending`; editing an `Approved`/`Hidden` article → back to `Pending`, unpublished, `HideReason` cleared) live on `IAnalystService` and are ownership-checked against the caller's own userId; admin-side transitions (`ApproveArticleAsync`, `HideArticleAsync`) live on `IArticleService`. An analyst can never publish directly or touch another author's article.
     - **Analyst self-service** (`/analyst`, Phase 2) — entered from a card on `/account/profile` shown only to analysts. Profile bio + photo (upload/replace/delete, with old R2 files cleaned up on replace/delete — note this correctly avoids the `ArticleService.DeleteAsync` storage-leak gap) and full CRUD over their own articles; the category picker is never shown since `Analytical` auto-assigns.
     - **Admin section** (`/admin/analytics`, Phase 3) — three tabs (المحللون / المقالات / بانتظار المراجعة) with counts; the pending queue is ordered oldest-first so it actually drains. Article titles and analyst names cross-link to detail pages. Actions: approve, hide (requires a reason, surfaced back to the analyst on their edit page), delete, and remove-analyst-designation (idempotent `RemoveAnalystDesignationAsync`; the analyst's existing articles are deliberately left intact and still manageable here). All confirmations use the established Bootstrap-modal pattern, never `confirm()`.
     - **Public surfaces** — a homepage تحليلات وآراء strip (latest 10, sitting directly under the stock filter results and *above* آخر المقالات) linking to `/analytics`; the `/analytics` listing (paginated, newest-first, search spanning article title/content **and** analyst name); and public analyst pages at `/analysts/{userId}` (photo, bio, searchable+paginated list of that analyst's published articles). All three go through `ArticleService.PublicAnalyticalQuery`, a single `IsPublished && Type == Analytical` gate, so a pending/hidden article can't leak onto any of them. Cards render from one shared partial (`_AnalyticalArticleCard`) — image, analyst photo+name (default person icon when the author has no `AnalystProfile`, e.g. an admin author), title truncated at 120 chars, like count — with CSS clamps keeping every card the same height.
     - **Likes & comments** (`ArticleLike`/`ArticleComment`, generic on `Article` so enabling them for another type is a controller change, not a schema one) live on the shared `/articles/{id}` detail page, which switches to an analyst byline + engagement block when `Type == Analytical`. All interactions are AJAX against `/api/articles/{id}/like` and `/api/comments/...` using the `RequestVerificationToken` header. One like per user is enforced by the unique `(ArticleId, UserId)` index; a user may edit/delete only their own comment, while `SuperAdmin/Admin/Editor` may delete any (`DeleteCommentAsAdminAsync`, which skips the ownership check and must therefore only be reached from that role-gated branch). Logged-out visitors see counts and comments read-only.
10. **Videos** (public, `/videos`) — admin-curated YouTube videos organized by `VideoCategory`. Admins paste a YouTube link; the server extracts/normalizes the video ID, validates it via YouTube's keyless oEmbed endpoint (real + embeddable), and stores the auto-filled title + thumbnail. Uniqueness is enforced on `YouTubeVideoId` (not the raw URL). The homepage shows the latest 6 as a horizontal-scroll strip; the listing page adds server-side search/category-filter/pagination. Both render as **click-to-embed facades** (thumbnail + play overlay → live `<iframe>` only on click), never live iframes on load. Follows the Article Controller→Service→EF pattern; adds `IYouTubeService` (oEmbed, mirrors `GoldPriceService`'s `IHttpClientFactory`+`System.Text.Json` pattern) and a `VideoCategory` lookup whose deletion is blocked while videos reference it.
11. **Homepage banners** (`Banner` model, `/admin/banners`, `SuperAdmin,Admin,Editor`) — admin-managed image + title + optional description, shown on the homepage as a Bootstrap-native carousel slider (no new JS library) directly under the hero header and above the search form. Fields: `ImagePath` (uploaded via `IStorageService`, `banners` folder, image required only on create), `TitleAr`, `DescriptionAr?`, `DisplayOrder` (ascending — smallest shows first), `IsActive` (toggle without deleting). `HomeController` fetches only `IsActive` banners ordered by `DisplayOrder` via `IBannerService.GetActiveOrderedAsync()`; an empty set simply hides the carousel (`@if (Model.Banners.Any())`). Follows the plain Controller→Service→EF pattern (no categories, no approval workflow — simpler than Articles/Videos).
12. **فتاوى المال** (`FatwaQuestion`, public `/fatawa`, admin `/admin/fatawa`, `SuperAdmin,Admin,Editor`) — Islamic-finance Q&A. A logged-in user submits a question (`POST /fatawa/ask`, max 5 pending per user, 10–2000 chars); guests see the hero + "اطرح سؤالك" button that goes to `/account/register?returnUrl=/fatawa?ask=1` (`Register` now honours `returnUrl`, same shape as `Login`). **A question is never public until answered *and* published**: `IFatwaService.PublicQuery` (`IsPublished && Answer non-empty`) is the single gate for `/fatawa` and the home strip. `FatwaStatus` (`Pending=1`/`Answered=2`/`Published=3`, int — never renumber) is maintained **only** by `FatwaService.SaveAnswerAsync`, which enforces the invariants `Published ⟹ has answer` and `IsFeatured ⟹ IsPublished` (unpublishing clears Featured, blanking the answer returns to Pending). Admin answers with a Quill editor (HTML, `Html.Raw` on public pages — hence Editors-and-up trust model as articles, no image upload). `IsFeatured` questions fill the home page **أهم الأسئلة** section (latest 4, → `/fatawa`). Cards render from one shared partial `Views/Shared/_FatwaCard.cshtml` (+ `wwwroot/js/fatwa.js` for the clamped-answer "قراءة الإجابة كاملة" toggle). `UserId` is nullable/`SetNull` so deleting a user keeps the Q&A; the asker's identity is admin-only, never shown publicly.

## Architecture Overview
- **Stack**: ASP.NET Core 8.0 MVC, C# (nullable + implicit usings enabled), server-rendered Razor views (no SPA framework). EF Core 8 + SQL Server, code-first migrations. Bootstrap 5 RTL + Tajawal font + jQuery/Select2 on the frontend. No automated tests, no CI/CD — a clean `dotnet build` plus manual click-through is the only quality gate today.
- **Layering** (applies to every feature but one): `Controller → Service Interface (Services/Interfaces) → Service Implementation (Services/Implementations) → AppDbContext`. Services are registered scoped in `Program.cs`. Known exception: `PortfolioRequestController` talks to `AppDbContext` directly.
- **Validation lives on ViewModels, not Models.** `Models/` entities carry no `DataAnnotations`; all `[Required]`/`[Display]`/etc. live on `ViewModels/*`. This is the most consistently enforced convention in the codebase.
- **Routing**: attribute routing everywhere, no MVC Areas. Admin controllers sit under `Controllers/Admin/*` with `[Route("admin/...")]` + role-based `[Authorize]`; public controllers use root-level routes (`/recommendations`, `/zakat`, etc.).
- **Auth**: ASP.NET Identity, custom `AppUser`, a `UserRole` enum (`SuperAdmin, Admin, Editor, User`) surfaced as a claim via a custom claims factory so `[Authorize(Roles = "...")]` works against it. Public self-registration always creates a `User`; elevated roles are only ever created by a SuperAdmin.
  - **There is exactly one authentication scheme and one cookie.** "Admin" is a role claim, not a separate scheme — so a single `LoginPath` has to serve both audiences. `ConfigureApplicationCookie` therefore sets `LoginPath = "/account/login"` **and** an `OnRedirectToLogin` handler that sends challenges under `/admin/*` to `/admin/login` and everything else to the public login. Before this, `LoginPath` was hardcoded to `/admin/login`, so *every* unauthenticated challenge site-wide dumped public visitors on the admin panel's login form. Don't "simplify" that handler away.
- **Validation messages are Arabic by default, globally** — see coding-standards for the three mechanisms. Don't hand-roll Arabic strings for standard rules (`required`, `min`, `max`, `number`); they're already covered.
- **Storage**: Cloudflare R2 via `AWSSDK.S3`, abstracted behind `IStorageService`, with automatic fallback to local disk (`LocalStorageService`) when R2 config is absent — this is what makes local dev work without cloud credentials.

## Key Workflows

**Shariah classification** — every `Stock` has a `ShariahStatus` plus a finer `PurityGrade` flags value; `StockFinancialReview` versions the underlying per-period review that classification is based on. `Stock` also carries two company-level figures used only by the capital purification calculator — `TotalCompanyShares` (`long?`, bigint) and `TotalCompanyAssets` (`decimal?(18,2)`), both admin-entered on the stock form under a **بيانات الشركة المالية** fieldset and both `NULL` for every stock until an admin fills them in. The calculator's third input, نسبة الأنشطة الربوية, is the **existing** `NonShariahInvestmentRatio` screening ratio — not a new field.

**Guest gates** — the established way a login-required page stays publicly reachable: no class-level `[Authorize]` blocking the entry point, an auth check at the top of the `Index` action, and a full standalone `GuestGate.cshtml` view (H1 + a real teaser paragraph so the page is worth indexing, then إنشاء حساب مجاني / تسجيل الدخول buttons carrying `?returnUrl=<this page>`). Used by `/calculator`, `/zakat`, `/capital-purification`, `/stocks/{ticker}`, and — added later, on controllers that keep their class-level `[Authorize]` — `/recommendations`, `/recommendations/wallet`, `/recommendations/portfolio` via `[AllowAnonymous]` on `Index` alone. Prefer this over `Challenge()`, which produces a bare redirect and no indexable content.

**Recommendation visibility & validity** (current model — this has evolved past what older docs describe as a hardcoded enum):
- Each recommendation (general or private) has a `RecommendationTypeId` FK to a `RecommendationType` **lookup table** (`NameAr`, `IsExpiredMarker` bool), managed on an admin "Manage Types" page — not a fixed C# enum.
- General recommendations (`StockRecommendation`) carry an admin-only `IsHidden` flag, toggled via a Visible/Hidden radio button on the admin Create/Edit forms. Hidden ones are excluded from the recommendations list *and* the wallet's stock picker for everyone except admins; admins still see them (badge-marked) for management purposes.
- Validity — "سارية" (valid) vs "منتهية" (expired) — is derived purely from the assigned type's `IsExpiredMarker`, not from any date/age. It's shown as a badge on the general table (all users) and as a "(منتهية)" tag in the wallet dropdown.
- Private recommendations (`UserStockRecommendation`, one per user per stock) never show hidden/validity badges in the table, but do get a "(خاص)" tag in the wallet dropdown, combined with "(منتهية)" when applicable, e.g. "(خاص - منتهية)".
- Private recommendations also collect a narrower field set than general ones: `YtdChangePercent` isn't shown or editable at all (form input and table column both omitted), and `GeneralTrend` is optional — left blank, it's stored as an empty string and always displayed as "غير محدد". General/admin recommendations still require `GeneralTrend` and still show/edit `YtdChangePercent`.

**Two "calculation" features share vocabulary, not architecture** — `/calculator` is stateless with no DB involvement; `/calculations` is the persisted, full-CRUD version. Treat them as unrelated when making changes.

**The request → admin-approval gate is a reused pattern**, not unique to one feature — portfolio requests and recommendation access both follow `Pending → Approved/Rejected` reviewed by an admin, rather than self-serve payment. A new premium feature would likely follow the same shape.

## Important Assumptions & Risks
- **No automated tests or CI/CD exist.** Every change is verified manually (build + click-through); a clean build is necessary but not sufficient.
- **`appsettings.json` is not gitignored** — only `secrets.json`/`.env` are excluded. Keep real credentials out of it by discipline, or move local dev config to `dotnet user-secrets`. Treat any committed credentials as a live, not hypothetical, risk.
- **Known inconsistencies elsewhere in the codebase** (don't assume they're fixed unless you check): `ArticleService.DeleteAsync` doesn't clean up the associated storage file; `CategoryFormViewModel` still has no `DataAnnotations` at all, unlike newer forms — `ArticleFormViewModel` was brought up to the newer convention (`[Required]` on `TitleAr`/`ContentAr`/`ArticleCategoryId`) when the article-category feature was added, and `StockFormViewModel` is now *partly* annotated (`[Range]` on the two company-financial fields only; its older fields are still bare).
- **A simple-type action parameter does not bind from a posted form field on this project's login action** — `AccountController.Login(LoginViewModel vm, string? returnUrl)` only ever saw `returnUrl` from the query string, so the hidden `returnUrl` form field was silently dead and *every* guest gate's "تسجيل الدخول" button dropped the user on `/` after login. Fixed by carrying it in the form's action URL (`asp-route-returnUrl`) and re-stashing it in `ViewBag` on the POST so it survives a failed attempt. If you add another returnUrl-carrying form, follow that shape rather than a hidden input.
- **Business model is inferred from feature structure**, not an explicit pricing page: free screening/articles → login-gated calculator persistence → lead-gen portfolio requests → admin-vetted recommendations access.
- **Deployment is shared IIS hosting (SmarterASP.NET).** DB migrations are applied separately (`dotnet ef database update` / VS Package Manager `Update-Database`) from publishing the app binaries. A running app process holds file locks that a plain FTP publish cannot override — use an `app_offline.htm` drop, a control-panel app-pool stop, or (preferred going forward) Web Deploy instead of raw FTP.
